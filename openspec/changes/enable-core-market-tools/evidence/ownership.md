# Five-tool ownership and independent-build evidence

Audit date: 2026-11-14. Scope: current TypeScript imports/native command adapters, Rust implementation families and background ownership. Source pointers below identify migration seams, not completed migrations or a released API catalog. No task checkboxes or runtime gates are changed by this record.

## Ownership rule

A tool owns its UI, translations, domain rules, configuration schema/migration, workflows and background JavaScript entry. Public SDK owns versioned DTOs, capability/error/event contracts and session-bound calls. Rust owns OS calls, authoritative work state, scheduling delivery, queue/lease limits, permission checks and generation revocation. The composition layer owns provider registration and selected package installation, without tool business rules or ID-specific rendering. A compiled native provider does not by itself make a tool package ready.

The current five `metadata.json` descriptors are bundled-module records: `main` points to `plugins/<directory>`, and their permissions/contributions use the trusted static adapter. None is a standalone Web v2 package manifest. All five need a package-owned HTML entry, manifest, package dependencies/lock, public SDK calls and separate native acceptance before being advertised as installable.

## Awake — `zero.awake`, `src/plugins/caffeine/`

- Package/domain: `CaffeinePanel.tsx`, `AwakeSettings.tsx`, `caffeineDuration.ts`, `caffeineSchedule.ts`, `caffeineState.ts`, `caffeinePresentation.ts`, `i18n.ts`, `caffeine.css`, `plugin.tsx`, `metadata.json`. Duration parsing, until-time/DST preview, presentation timing, battery-policy choices and config migration belong to Awake. Native enforcement revalidates submitted bounds and policy; UI timers do not own keep-awake expiry.
- Private imports to remove: `core/pluginHost/pluginModule` (descriptor/panel/settings types), `core/windowing/useSurfaceActivity` and `surfaceActivityCore`, `core/preferences/i18n`. Replace with stable SDK context/lifecycle/localization contracts or package-local presentation helpers. Keep `react` and `lucide-react` as explicit versioned package dependencies.
- Native seams: `useCaffeinePlugin.ts` directly imports Tauri core/event and reads `get_caffeine_state`, `get_awake_preferences`, mutates `set_caffeine_schedule`/`toggle_keep_awake` through its `mutate(command, input)` helper, and listens to `caffeine-state-changed`. `AwakeSettings.tsx` calls `get_awake_preferences`, `get_awake_power_state`, `update_awake_battery_policy`. These must become typed public capability calls/events, without a raw command-string API.
- Provider/authority: `src-tauri/src/commands/caffeine.rs`, `services/caffeine.rs`, `caffeine_runtime.rs`, `caffeine_schedule.rs`, `awake_preferences.rs`, `power_events.rs`. Platform power assertion/process/thread, continuous/wall clock, validated expiry, battery state reads, fail-safe release and live generation checks remain Rust. `caffeine_schedule.rs` currently combines bounded validation and timing authority; its OS clock and remaining-time authority stay native. `awake_preferences.rs` contains tool policy/defaults that require explicit package schema/migration and a validated native enforcement description rather than renaming the entire file as generic provider.
- Background: keep-awake remains active with hidden UI; UI presentation clock only runs for active surfaces. Generic power/task owner must be `(plugin ID, digest, generation, lease)`; disabling Awake releases its lease, closing UI does not. Complex future schedules wake the package background entry; an already submitted expiry runs natively.

- Native seams: `bingWallpaperService.ts` directly injects Tauri `invoke` into `bingWallpaperServiceCore.ts`. - Provider/authority: `src-tauri/src/commands/bing_wallpaper/{mod,window}.rs`; `services/bing_wallpaper/{mod,wallpaper,automation,automation_runtime,automation_store,policy}.rs`. Bounded HTTP, cache files/previews, output approval, OS wallpaper setting and cancellation stay native capabilities. `policy.rs` market-day/publication/retry selection and the business check/apply workflow in `automation.rs` must move to Paper's package-owned background module. Durable scheduling/occurrence delivery, queue serialization, generation revocation and side-effect deduplication remain host authority. Current Rust daily loop is not evidence of an independent package background runtime.
- Background: only enabled daily automation runs startup/cross-day/resume checks. Hidden WebView must execute package policy on demand, then terminate within the 60s bound; no permanent plugin JS timer and no automatic opt-in. Disabling Paper cancels its schedule/download/cache leases without affecting other tools.

## Launch — `zero.launch`, `src/plugins/quickLauncher/`

- Package/domain: `QuickLauncher{App,Panel,View}.tsx`, `useQuickLauncher.ts`, `quickLauncher{Model,Scheduling,Shortcuts}.ts`, `contracts.ts`, `i18n.ts` and descriptor. Query debounce/revision, keyboard row numbering, display and search preferences belong to Launch.
- Private imports to remove: bundled module types; `core/preferences/i18n`; `core/windowing/useSurfaceActivity`; `services/useGlobalShortcuts`. `QuickLauncherApp.tsx` uses Tauri `getCurrentWindow` for focus/dismissal. Public window/shortcut contributions must replace these host implementations.
- Native seams: `quickLauncherService.ts` injects Tauri `invoke` into `quickLauncherServiceCore.ts`: `get_quick_launcher_snapshot`, `refresh_quick_launcher_index`, `search_quick_launcher`, `get_quick_launcher_icon`, `get_quick_launcher_icons`, `refresh_quick_launcher_running_state`, `get_quick_launcher_running_items`, `activate_quick_launcher_item`, `show_quick_launcher_window`, `hide_quick_launcher_window`. `useQuickLauncher.ts` subscribes to `RUNNING_UPDATED_EVENT` and uses bounded presentation refresh timers.
- Provider/authority: `src-tauri/src/commands/quick_launcher.rs`; `services/quick_launcher/{mod,catalog,cache,contracts,model,search}.rs` and `platform/{macos,windows,unsupported}.rs`. OS catalog/watch/icon/running-app state and activation of host-issued indexed IDs stay native. `search.rs` query matching/ranking, `model.rs` product defaults and bundled aliases are domain policy requiring separation from OS indexing: either package owns ranking over bounded provider results or explicitly declares a shared, versioned search primitive with package-supplied policy. Do not simply rename all current search code a provider and leave Launch ranking hardcoded in host.
- Background: `QuickLauncherState` owns index/watch state; `bundled_plugins.rs::start_quick_launcher` currently eagerly initializes it for the static lifecycle. Generic activation must initialize lazily for an installed/enabled owner, and stop watcher/shortcut/window contributions on disable. Search queries and history remain local and must not become market diagnostics.

## File — `zero.file`, `src/plugins/file/`

- Package/domain: `FilePanel{,Entry}.tsx`, `FileQualityDetails.tsx`, `useFileConversion.ts`, `fileServiceCore.ts`, `contracts.ts`, translations, descriptor and conversion domain/quality algorithms in `engine/`. The small package owns UI, conversion workflow/quality policy and an explicit engine resource declaration; it must not copy all heavyweight engines into its archive.
- Private imports to remove: bundled module types; `core/preferences/i18n`; `core/ocr/contracts` in `engine/{pdfOcr,pdfScan,pdfToDocx}.ts` and inline import in `FileEngineApp.tsx`; `FilePanel.tsx` directly uses Tauri window APIs. `react`, `react-dom`, `lucide-react`, `docx`, `docx-preview`, `pdfjs-dist` are explicit third-party dependencies whose distribution size/license/engine ownership must be decided separately.
- Native seams: `fileService.ts` injects Tauri invoke/event into `fileServiceCore.ts`: capabilities/refresh/provider selection/configuration; choose/inspect inputs; enqueue/list/queue snapshot/start/cancel/remove/retry/clear completed; open/reveal outputs. Exact 16-command map is `FILE_CONVERSION_COMMANDS`; three `zero://file-conversion/{job,capabilities,queue}-updated` events are typed in that file. `engine/FileEngineApp.tsx` separately calls `file_engine_ready`, `file_engine_inspect_fonts`, `prepare_file_page_ocr`, `upload_file_page_ocr`, `file_engine_write_output`, `file_engine_print_rendered`, `file_engine_complete`, `file_engine_read_input`, `file_engine_progress`, and listens to `FILE_ENGINE_RUN_EVENT`/`FILE_ENGINE_CANCEL_EVENT`.
- Provider/authority: `src-tauri/src/commands/file.rs`; `services/file/{runtime,queue,capabilities,preferences,provider,built_in,process,discovery,validation,artifacts,output,result_actions,engine_bridge,native_print,fonts,quality,editable_output,word_macos,word_windows,libreoffice}.rs` and `engine_bridge/ocr.rs`; `src-tauri/capabilities/file-engine.json`; existing signed engine release policy. Package owns conversion/quality policy; the isolated signed engine remains a separate narrow resource/runtime and cannot gain generic process execution.
- Background/platform: file jobs/queue survive UI closure according to existing authoritative job state; disable/update drains/cancels its owner and prevents late outputs. File engine signing/approval and real PDF/DOCX quality/device gates remain mandatory and currently separate from this builder's synthetic fixture evidence.

## Shared composition and remaining migration interfaces

`src/appShell/bundledPluginModules.ts`, selected `bundledPluginCatalog.*.ts`, `src/main.tsx`, `src-tauri/src/bundled_plugins.rs` and `src-tauri/src/lib.rs` currently compose static tool UI/services. Existing lifecycle switches on canonical IDs are migration seams, not the target generic package API. Public contributions must route isolated installed-package sessions, with no static panel fallback in core/standard. `core/preferences/i18n` helpers are not implicitly public just because all tools use them. Shared stable DTOs move to a self-contained SDK; generic visual helpers are either an explicitly versioned library or tool-owned code.

For each proposed native method, freeze permission, symmetric Rust/TS DTO, capability/version, owner tuple, deadline, cancellation/late-result semantics, resource limit and lifecycle cleanup before connecting a migrated package. This document identifies capability families, not invented shipping method names. Provider methods must not accept a private Tauri command string, arbitrary process/path activation or another tool's owner. Current direct imports of peer tool directories were not found in these five tool source trees; private host imports and direct Tauri adapters are present in every tool.

## Independent build foundation delivered in this slice

- [`scripts/plugin-packages/build.mjs`](../../../../scripts/plugin-packages/build.mjs) provides `buildPluginPackage({pluginRoot,sdkRoot,outputDir,signal?,limits?})`, `checkPluginPackage({bytes|archivePath,signal?,limits?})` and build/check CLI. See its [input/API contract](../../../../scripts/plugin-packages/README.md).
- Actual fixture builds use TypeScript compiler AST, Vite and JSZip, inspect decompressed root-layout contents, measure SHA-256 and compare deterministic archive bytes. Private host/peer/type-only/dynamic/transitive/alias/Tauri/node_modules-symlink imports are rejected. Legitimate aliases, declared/transitive libraries, a real installed React dependency, a library with separate type/runtime entries, and a background shared chunk build successfully.
- Asset checks cover HTML, CSS, symlinked assets, `new URL(..., import.meta.url)` and worker entry imports. Unsafe archive paths, missing main, compressed/expanded/source limits and cancellation are tested. Official IDs may build; checker explicitly returns `publisherVerified:false` and `releaseApproved:false`.
- This does not migrate the five tools, produce official downloadable archives, verify signatures, open the runtime gate, start hidden background sessions or establish native acceptance. Those remain independent implementation/release gates.

## Verification record

`node --test tests/integration/pluginPackages/build.test.mjs`: 70 tests passed, 0 failed on Node v24.20.0. Initial tests ran against unimplemented build/check exports and failed 22/22. Follow-up negative fixtures first demonstrated actual missing rejections for relative node_modules, HTML/CSS assets and `new URL` reads; each was implemented and rerun green. A typed dependency fixture first demonstrated incorrect `.d.ts` runtime selection and then passed with Vite runtime resolution. A final fixture built against the actual self-contained `src/sdk` source root, with no `src/core` input; its first run rejected declared SDK type dependencies and the corrected boundary admits declared type files/peer libraries. No shared test preparation, signing, commit, push, publishing, native-window acceptance or checkbox updates were performed by this slice.


### Review correction: Vite HTML direct asset reads

Review reproduced two actual privacy escapes: `meta[property="og:image"][content]` and `link[imagesrcset]` let Vite copy peer SVG bytes into a compressed archive while `sourceFiles` omitted that peer input. Two real artifact fixtures first failed by inspecting those leaked archive bytes (33 passing, 2 failing). The HTML regex guard was then replaced with Vite's bundled parse5 and its actual `DEFAULT_HTML_ASSET_SOURCES` registry, read using the TypeScript AST. Unsupported upstream registry layouts/filters fail closed. The accepted attribute syntax stays restricted to the previous local `src/href/poster/data` forms; meta assets, image source sets and SVG xlink references are rejected rather than newly enabled.

The final 70/70 run covers every current Vite HTML asset tag/attribute, all seven allowed meta names and seven properties, template contents and entity-encoded inline style URLs. Ordinary non-asset viewport/description metadata and local image assets still build, with the local asset's real path recorded. The implementation is coupled to the locked Vite distribution's bundled parser/registry layout and fails at startup rather than silently skipping a changed upstream layout.
